## 0. 先看懂全局：这套仿真到底是什么

拿到一个别人搭好的仿真工程，第一步不是跑命令，而是**搞清楚数据流向**。整个系统分两条链路：

```text
【主链路：MuJoCo 物理仿真】
SolidWorks 三维模型
    │ 导出（sw_urdf_exporter 插件）
    ▼
urdf/H1.urdf                 ← 机器人本体描述（link/joint/mesh/惯量）
    │ ① 修 mesh 路径
    │ ② MuJoCo 编译 URDF 并回存为 MJCF   ← mujoco/h1_imported.xml
    │ ③ 用脚本合并双夹爪 + 执行器 + 碰撞 + 传感器
    ▼
mujoco/h1_omnipicker.xml     ← 最终仿真模型（含桌子、方块、相机、home 姿态）
    │ ④ python -m mujoco.viewer 查看
    │ ⑤ teleop/h1_pico_teleop.py 遥操作（Placo IK + PICO）
    ▼
交互式物理仿真 / 未来的 VLA 训练数据采集

【旁路：ROS 2 / RViz2 仅查看模型】
urdf/H1.urdf + launch/display.launch.py ──► RViz2 里看机器人外观
（与 MuJoCo 仿真互不相干，学习阶段可以不装 ROS 2）
```

**几个初学者必须先理解的概念：**

| 术语 | 一句话解释 |
|---|---|
| **URDF** | Unified Robot Description Format，ROS 世界通用的机器人描述文件（XML），描述连杆、关节、网格、惯量。SolidWorks/Onshape 都能导出。 |
| **MJCF** | MuJoCo 自己的模型格式（也是 XML），比 URDF 多了物理仿真专属内容：执行器、传感器、接触材质、keyframe 等。 |
| **MuJoCo** | 高速物理仿真器，机器人学习领域的事实标准之一（lerobot 也用它）。 |
| **执行器 actuator** | MJCF 里的"电机"。本工程用 `position` 位置执行器：给一个目标角度，内置 PD 控制器输出力矩去跟踪。 |
| **keyframe** | 模型里保存的一组完整状态（关节角等）。`home` 是这套仿真的唯一初始基准姿态。 |
| **正运动学/逆运动学** | 正：已知关节角 → 算末端(TCP)位姿。逆：已知想要的 TCP 位姿 → 反解关节角（IK）。遥操作必须用逆。 |
| **Placo** | 基于 Pinocchio 的数值 IK 库，把"多任务跟踪"组织成一个 QP（二次规划）问题实时求解。 |
| **TCP** | Tool Center Point，工具中心点。夹爪上定义的"抓取中心"坐标系，遥操作时手柄控制的就是它。 |

## 1. 认识起点：URDF 文件长什么样

H1 本体描述在 `urdf/H1.urdf`（1090 行，SolidWorks 导出）。核心结构只有三种标签：

```xml
<robot name="H1">
  <link name="base_link">          <!-- 一个连杆：躯干底座 -->
    <inertial> <mass value="14.282"/> ... </inertial>   <!-- 质量/惯量 -->
    <visual>   <geometry><mesh filename="package://h1_description/meshes/base_link.STL"/></geometry> </visual>
    <collision> ... </collision>   <!-- 碰撞几何 -->
  </link>

  <joint name="Left_J1" type="revolute">   <!-- 一个转动关节 -->
    <parent link="waist_link_J2"/> <child link="left_link_J1"/>
    <axis xyz="0 1 0"/>                    <!-- 旋转轴 -->
    <limit lower="-2.6" upper="2.6" effort="88" velocity="2.0"/>  <!-- 限位/力矩/速度 -->
  </joint>
  ...（更多 link / joint）
</robot>
```

H1 的机械结构（共 **18 个转动关节 / 19 个连杆**）：

| 部位 | 关节 | 说明 |
|---|---|---|
| 腰部 | `J1`(=waist_J1), `waist_J2` | yaw + pitch，2 自由度 |
| 左臂 | `Left_J1` ~ `Left_J7` | 7 自由度机械臂 |
| 右臂 | `Right_J1` ~ `Right_J7` | 7 自由度机械臂（注意 `Right_j6` 是小写 j，历史遗留命名） |
| 头部 | `head_j1`, `Head_j2` | yaw + pitch |

### ⚠️ 本工程踩过的第一个坑：关节限位全 0

对比 `robot_simulation_model/H1/urdf/H1.urdf`（原始导出）会发现：

```xml
<limit lower="0" upper="0" effort="0" velocity="0"/>   ← 原始导出：全 0！
```

SolidWorks 导出器**不会自动填**电机参数。全 0 意味着关节完全锁死、无法驱动。
搭这套仿真的前辈在 `mujoco/h1_for_import.urdf` 里手动补全了限位/力矩/速度（这份文件
是修好后的版本，还加了左右 TCP link，共 20 joint / 21 link）。

**经验：拿到任何 SolidWorks 导出的 URDF，第一件事就是检查每个 joint 的 `<limit>` 和
`<dynamics>`（阻尼）是否为 0。**

## 2. 第一步：让 MuJoCo 直接"吃"URDF

MuJoCo 可以直接加载 URDF（内部先转成 MJCF 再编译）。但有两个规则：

1. **不认识 `package://` 协议** —— 这是 ROS 的资源寻址方式，必须改成普通相对路径；
2. **mesh 相对路径以"模型文件所在目录"为基准** —— 这就是为什么工程里所有 MJCF
   都放在 `mujoco/` 子目录、meshes 放在旁边的 `meshes/`（`../meshes/xxx.STL`）。

复现命令（在 `H1_1/` 目录下执行，**所有命令都在这个目录跑**）：

```bash
conda activate lerobot312        # 本机环境，含 mujoco 3.8.0 + placo
cd /home/mjq/robot_item/lerobot-main/H1_simulation_model/H1_1

# ① 把 package:// 替换成相对路径，生成一份 MuJoCo 可读的 URDF
python -c "
import re
src = open('mujoco/h1_for_import.urdf').read()
fixed = re.sub(r'package://h1_description/meshes/', '../meshes/', src)
open('mujoco/_step1_fixed.urdf', 'w').write(fixed)
"
```

> 注意：`h1_for_import.urdf` 的中文注释里含 `--check-model`（双连字符），严格 XML
> 解析器（ElementTree）会报错，但 MuJoCo 自己的解析器是宽容的，不影响使用。
> 这也是一个坑：**XML 注释里不要出现 `--`**。

## 3. 第二步：URDF → MJCF 转换（编译后回存）

思路：让 MuJoCo 编译 URDF，再用 `mj_saveLastXML()` 把**编译产物**存成 MJCF。
编译过程会自动做单位换算、惯量整理、几何合并。

```python
import mujoco
m = mujoco.MjModel.from_xml_path('mujoco/_step1_fixed.urdf')   # 编译
mujoco.mj_saveLastXML('mujoco/_step2_imported.xml', m)          # 回存 MJCF
```

本机实测输出：

```text
① URDF 编译成功 | nq=18 nv=18 nbody=19 nmesh=19
② MJCF 回存 -> mujoco/_step2_imported.xml
```

（`nq`=广义位置数=关节数 18；`nbody`=刚体数 19；`nmesh`=网格数 19——和 URDF 完全对上）

生成的 MJCF 开头长这样（mesh 路径已自动转成相对路径）：

```xml
<mujoco model="H1">
  <compiler angle="radian"/>
  <asset>
    <mesh name="base_link" content_type="model/stl" file="../meshes/base_link.STL"/>
    ...
```

工程里的 `mujoco/h1_imported.xml` 就是这一步的产物（前辈留下的版本）。

## 4. 第三步：合并两只 OmniPicker 夹爪

这是整套工程里**最核心的一步**，涉及两个方向、三种模型文件，先理清"谁服务谁"：

| 文件 | 格式 | 服务对象 | 内容 |
|---|---|---|---|
| `scripts/compose_h1_omnipicker.py` | 产出 URDF | RViz / Placo IK | 把夹爪 URDF 挂到 H1 腕部，加 TCP link |
| `mujoco/omnipicker_component.xml` | MJCF 组件 | build 脚本 | 夹爪的 8 个手指关节 + 四连杆约束 + 1 个归一化开合执行器 |
| `scripts/build_h1_omnipicker_mjcf.py` | 产出 MJCF | MuJoCo 仿真 | 把上面两者在 **MJCF 层面**合并成带执行器/碰撞/传感器的完整模型 |

### 4.1 夹爪怎么装上去（挂载变换）

H1 的手腕沿局部 **-Z** 方向伸出，而官方 OmniPicker 沿 **+Z** 安装，所以要旋转 180°
（左右手用不同的旋转轴，让宽手指朝外）：

```python
add_gripper(..., side="left",  parent_link="Left_Link_J7",
            xyz=(0, 0, -0.045), rpy=(0, math.pi, 0))    # 绕 Y 翻转
add_gripper(..., side="right", parent_link="Right_Link_J7",
            xyz=(0, 0, -0.045), rpy=(math.pi, 0, 0))    # 绕 X 翻转
```

TCP（抓取中心）定义为夹爪基座前方 13 cm：`<origin xyz="0 0 0.13"/>`。

### 4.2 build 脚本做了什么（建议逐函数精读，共 413 行）

| 函数 | 作用 | 学习点 |
|---|---|---|
| `build()` 主流程 | compiler/option/visual/defaults 设置 | 仿真步长 1ms、`implicitfast` 积分器 |
| `h1_joint_class()` | 按电机 BOM（HBN110-087 等型号）给每个关节分类 | **不同关节用不同 PD 增益**：腰部 kp=5500，末端 kp=600——越靠近末端电机越小 |
| `add_h1_actuators()` | 给 18 个关节各生成一个 `position` 执行器 | 位置控制的含义：`ctrl` 写目标弧度即可 |
| `add_gripper()` | 挂夹爪、加腕部力矩传感器 site 和 TCP site | 夹爪执行器 kp=40/forcerange=±0.8Nm ≈ 官方 30N 抓力 |
| `add_collision_geoms()` | **视觉网格不参与碰撞**，另用 AABB 包围盒（0.48 倍尺寸）做碰撞体 | 用盒子替代 STL 碰撞是仿真提速的关键手法；手指用高摩擦 `finger_collision` 类 |
| `add_sensors()` | 全关节 pos/vel/力矩 + 腕部六维力 + TCP 位姿 + 指尖触觉 | 共 142 个传感器，为数据采集准备 |

**复现命令（生成"原始合并模型"，注意脚本会拒绝覆盖调好的最终文件）：**

```bash
python scripts/build_h1_omnipicker_mjcf.py \
    --h1 mujoco/_step2_imported.xml \
    --gripper mujoco/omnipicker_component.xml \
    --output mujoco/_step3_raw.xml
```

本机实测输出：

```text
③ 合并模型生成 OK
④ 生成的原始模型可加载 | nq=34 nu=20 nbody=37
```

（`nu=20` = 18 个本体关节执行器 + 2 个夹爪开合执行器；`nq=34` = 18 本体 + 每侧 8 个手指关节）

### 4.3 夹爪的单执行器设计（值得学习）

OmniPicker 每侧有 8 个手指关节，但**只有 1 个执行器**。手指间运动由 MJCF 的
`<equality>` 约束保证：

- `narrow_four_bar` / `wide_four_bar`：`connect` 约束实现四连杆联动；
- `opposed_finger_drive`：`joint` 约束让相向手指反向耦合。

所以遥操作时 Trigger 只需写一个 0~1 的开合值，四根手指自动协调开合——
**机械耦合交给物理引擎，控制接口保持极简**。

## 5. 第四步：手工调出最终场景（h1_omnipicker.xml）

build 脚本的产物只是"裸机器人"。前辈在此基础上**手工编辑**出了最终的
`mujoco/h1_omnipicker.xml`（所以脚本对覆盖它有专门保护，需要 `--overwrite-working-model`）。
手工增加的内容：

- **场景物体**：`work_table` 工作桌、`green_bin` 绿色料箱、`red_cube_left/right`
  两个自由红色方块（各带 7 自由度 free joint —— 这解释了 qpos 从 34 变 48）；
- **三台相机**：`head_rgb`（头部，75°）、`left/right_wrist_rgb`（腕部，100°），
  即未来 VLA 模型的三视角观测；
- **`home` keyframe**：唯一初始基准（启动、B 键回零、A 键重置方块都读它）；
- **`left/right_teleop_target`** 可视化目标体，调试 IK 用。

### 数字对账表（模型自检的核心）

| 指标 | 值 | 组成 |
|---|---|---|
| `nq` | 48 | 18 本体 + 16 手指 + 7×2 两个方块自由关节 |
| `nu` | 20 | 18 关节位置执行器 + 2 夹爪开合执行器 |
| `nsensor` | 142 | 关节 pos/vel/力矩 + 腕部力 + TCP 位姿 + 指尖触觉 |
| `nbody` | 45 | 19 本体 + 2×(1 安装座+8 手指) + 桌/箱/2 方块 + 目标体 |

**任何一步改了模型，都应该重新数一遍这些数字是否对得上。**

## 6. 第五步：无界面物理验证（headless 冒烟测试）

不打开窗口也能验证模型正确性——加载、复位到 home、步进 2 秒看关节是否漂移：

```python
import mujoco, numpy as np
m = mujoco.MjModel.from_xml_path('mujoco/h1_omnipicker.xml')
d = mujoco.MjData(m)
kid = mujoco.mj_name2id(m, mujoco.mjtObj.mjOBJ_KEY, 'home')
mujoco.mj_resetDataKeyframe(m, d, kid)
mujoco.mj_forward(m, d)
for _ in range(2000):          # 2000 步 × 1ms = 2 秒
    mujoco.mj_step(m, d)
drift = np.abs(d.qpos[:7] - m.key_qpos[kid][:7]).max()
print(f'最大关节漂移 {drift:.4f} rad')   # 本机实测 0.0021 rad → 稳定
```

本机实测（RTX 5090 + EGL 离屏渲染一帧 720p 成功，画面完整）：

```text
2s 物理仿真完成 | 最大关节漂移: 0.0021 rad | 仿真稳定
```

## 10. 坑总结（按出现顺序）

1. **SolidWorks 导出的 URDF 关节限位全 0** → 手动补 limit/dynamics（第 1 节）；
2. **MuJoCo 不认 `package://`** → sed/python 替换成相对路径（第 2 节）；
3. **mesh 路径相对 XML 所在目录** → URDF/MJCF 必须放在和 meshes 匹配的目录层级（第 2 节）；
4. **XML 注释里不能有 `--`**（如 `--check-model`）→ MuJoCo 宽容、ElementTree 报错（第 2 节）；
5. **视觉网格 ≠ 碰撞几何** → 用 AABB 盒碰撞提速，STL 只用来看（第 4.2 节）；
6. **不要直接覆盖 `h1_omnipicker.xml`** → build 脚本有保护旗标，最终场景是手工调的（第 5 节）；
7. **改模型后必须重新对账**：nq/nu/nsensor/nbody 四个数字 + `--check-model`（第 5、7 节）；
8. **关节命名不统一**（`Right_j6`/`Right_J6`、`head_j1`/`Head_j2` 大小写混用）→ 写代码引用名字时逐字核对，别"看着像"就拼。

## 15. 踩坑实录（本次实战的精华，按"现象→真相→修法"）

1. **夹爪"卡死"在 -0.43 rad**（Step 6 最大的乌龙）
   - 现象：ctrl=1 时手指只张开一半，以为是碰撞或约束坏了；
   - 真相：position 执行器出力被 `forcerange=±0.8` 限幅，限幅力 vs 阻尼决定**蠕变速度**——
     不是卡死，是慢。500 步测试窗口太短，误把"慢"读成"停"；
   - 修法：对齐参考工程 kp=60/kv=4/forcerange=±1.2 后 1 秒到位（-1.199，与前辈分毫不差）；
   - 教训：**自测窗口必须长于系统收敛时间**，判断"卡死"前先看执行器力是否饱和。

2. **分档静摩擦没生效，全是 0.1**（Step 8 对照才抓到）
   - 现象：CLASS_PARAMS 里 frictionloss=0.03~0.25，编译出来 18 个关节全是 0.1；
   - 真相：URDF 的 `<dynamics friction>` 转成 MJCF 时**写死在关节元素上**（`frictionloss="0.1"`），
     MJCF 里元素自带属性 > class 默认值，分档默认被短路；
   - 修法：04 脚本挂 class 时 `joint.attrib.pop("frictionloss", None)`；
   - 教训：**URDF 带来的属性会潜伏在元素上**，用 class 分档管理参数时要先清掉旧属性。

3. **手指自碰（Step 5 左爪行程只有 0.23）**
   - 真相：四连杆夹爪的耦合杆和手指 STL 天然交叉，拿 visual 网格当碰撞体必然自卡；
   - 修法（标准套路）：mesh 全部改 `contype=0 conaffinity=0` 只渲染；
     每杆补 48% 尺寸 AABB 盒做碰撞（`contype=0 conaffinity=1`——机器人永不自碰，只碰环境）。

4. **keyframe 那串 48 个数字不能手抄**
   - qpos 顺序由 XML 树结构决定，两边模型差一个 body 顺序就全错；
   - 修法：加载参考模型，**按 joint/actuator 名字**把数值搬进自己的数组（07 脚本 `add_home_keyframe`）。

5. **XML 注释里不能写 `--`**：`h1_for_import.urdf` 的注释含 `--check-model`，
   MuJoCo 能容忍但 ElementTree 解析直接报错——程序化处理 XML 时留意。

6. **URDF 体检的误报**：`lower=0` 本身合法（肘关节就是 [0, 2.09]），
   只有 **lower==upper==0** 才是冻结关节。写检查脚本前先想清楚边界条件。

## 17. 前辈 VR 遥操作链路考古（做键盘版前先弄清"抄什么"）

- **硬件**：PICO 4 一体机（头显 + 双手柄 + 腰部 Motion Tracker），WiFi 连到装
  XRoboToolkit PC Service 的电脑，Python 端 `xrobotoolkit_sdk` 订阅设备位姿。
- **程序骨架** `H1_1/teleop/h1_pico_teleop.py`（继承 `MujocoTeleopController`）：
  - 控制语义是 **clutch（离合器）式相对控制**：按住手柄 Grip 时以当前 TCP 位姿为
    锚点，之后头柄的相对运动叠加到锚点上；松开 Grip 手臂冻结在原地；
    扳机 Trigger 控制夹爪开合；
  - 头显位姿 → 头部 yaw/pitch；腰部 Tracker → 腰部 yaw/pitch；
  - `R_HEADSET_TO_WORLD`：PICO 坐标 → MuJoCo 世界系的固定旋转
    （+X→−Y，+Y→+Z，+Z→−X）；
  - **安全限位三层**：工作空间盒 x[−0.05,1.00] y[−0.80,0.80] z[0.40,1.50]、
    距锚点平移 ≤0.5m、相对锚点旋转 ≤150°；
  - IK 用 placo：**posture 任务（soft 1e-3）钉住全部上身关节在 home**、
    trunk 任务（hard）钉腰/头、每臂一个 frame task；
    未激活臂用**关节空间** hold 任务（而不是世界系 frame task）——注释原文：
    这样手臂会随腰部自然运动，不会为维持世界系 TCP 反向补偿；
  - 控制频率 100Hz，每个周期只调**一次** `solver.solve(True)`，目标连续小步移动。
- 键盘版（Step 10）照抄了以上全部软件设计，只把输入源从"PICO 位姿流"换成
  "按键增量"。**键盘没有按住语义 → clutch 改为按 1/2 切换激活/冻结**。

## 19. placo IK 踩坑实录（第三部分精华）

1. **没有 posture 任务 → 关节漂到限位，误差卡在 100mm 不动**
   - 现象：只加 TCP frame task，反复 solve 后 waist_J1=3.14、Left_J1=−3.14 全饱和；
   - 真相：TCP 只约束 6 个自由度，18 关节剩下 12 维零空间无约束，
     求解器最小范数步会带着关节乱走；
   - 修法：`add_joints_task()` 钉 home，`configure("posture","soft",1e-3)`。

2. **连续 solve 不刷运动学 → 发散到 879mm**
   - 现象：连调 10 次 `solve(True)` 后再 update，TCP 跑到完全离谱的位置；
   - 真相：`solve(True)` 只把解写进 `state.q`，**不刷新运动学**；
     下一轮的雅可比在旧线性化点上求，步子越走越歪；
   - 修法：每轮 `solve(True)` 之后立刻 `robot.update_kinematics()`。

3. **关节名大小写**：URDF 里是 `Right_j6`（小写 j，前辈笔误但两模型一致），
   `head_j1`/`Head_j2` 同理——**按名字查，别按规律猜**。

4. **placo 0.9.16 API 与直觉不同的点**（`.pyi` 在 cmeel.prefix 下）：
   - `RobotWrapper` 永远有浮动基座（URDF 无 freejoint 时 pin 也会加，nq=7+18=25）；
   - FK 是有状态的：`set_joint → update_kinematics → get_T_world_frame(name)`
     （只收名字，不收 q）；MuJoCo 侧机器人固定在地上，基座 identity 直接对齐
     （Step 9 自测 0.000mm 证实）；
   - `solve()` 不是"迭代 N 次"而是"解一次问题"，每个控制周期调一次即可；
   - 从 MJCF keyframe 读关节角灌 placo 时要过滤：夹爪关节不在 IK URDF 里，
     `set_joints` 遇到不存在的关节名直接 RuntimeError。

5. **位置执行器链路最简单**：模型执行器名就是 `{joint}_position`，
   placo 解出的关节角**直接写 ctrl**；但要从 home 大幅运动时给 ctrl 加斜坡
   （本脚本 3 rad/s），否则 kp 有限+力限幅会让动作变成 Step 6 学过的"蠕变"。

6. **按激活键"模型消失"= 未捕获的 QP NaN 异常把 viewer 窗口带崩**
   - 现象：交互模式下按 1 激活手臂，整个模型/窗口消失（无头模式下是
     `RuntimeError: QPError: NaN in the QP solution`）；
   - 真相：`mj_resetDataKeyframe` 只写 qpos **不算派生量**，此时 `site_xpos`
     是全 0；若激活发生在第一次 `mj_step` 之前，锚点会被设成世界原点
     [0,0,0] —— 不可达目标让 QP 直接 NaN，异常没接住 → 主循环退出 → 窗口关闭；
   - 修法（三层）：① 读 site 前强制 `mj_forward`（消灭全 0 窗口，根治）；
     ② 锚点合法性校验（有限 + 在工作空间盒 ±5cm 内，否则拒绝激活）；
     ③ `solve()` 包 try/except，QP 偶发 NaN 时把 placo 状态拉回 MuJoCo 真实
     关节角、目标重锚当前 TCP，自愈而不是崩溃（已验证"头拧到限位再激活"
     这类奇异场景也能存活）。
   - 教训：**"消失"类现象先怀疑 NaN**；派生量（site_xpos/xmat 等）必须
    `mj_forward`/`mj_step` 之后才有效，reset 系列函数都不算。

7. **"按激活键模型消失"的真凶: viewer 的 C++ 层内部占用数字键**
   - 现象：GUI 遥操作中按 1/2 激活手臂后"模型瞬间消失"，但无任何 Python
     异常、qpos 有限、相机状态不变；无头模式永远复现不了；
   - 排查过程（三层防御全部布防后仍消失，说明方向错了）：
     ① v1.2 全类型异常捕获 → 零打印；② v1.4 相机看门狗（fixedcamid 监测）
     → 零打印；③ v1.5 每次激活自动快照 → 相机/物理/方块数值全程正常；
   - 决定性实验：写了一个"裸 viewer + 按键只打印"的隔离脚本，按 2
     （什么都不做）模型照样消失；按 3 出现绿色方块幽灵渲染；按字母 4 十几次
     完全正常。→ 问题在 viewer C++ 层对数字键的内部处理（帮助表未列出）；
   - 修法（v1.6）：激活键 1/2 改为 **N（左臂）/M（右臂）**，数字键一律
     拦下并提示"被 viewer 内部占用"。字母键经多轮实测安全；
   - 教训：**给 viewer 挑功能键只用字母**（避开数字/Space/方向键/Tab/`[]`/
     Esc/F1-F11）；"消失+无异常+无头复现不了"三件套 → 直接上**分层隔离
     脚本**（什么都不做/只算运动学/只推关节），比堆防御代码快十倍。

   - `create` 要求 root 不存在；已存在必须 `resume`；
   - 帧字典 key 与 features 一一对应 + 每帧一个 `task` 字符串，
     **禁止传 timestamp/frame_index 等保留键**；数组必须严格 float32；
   - 读回前必须 `finalize()`；
   - v3.0 视频布局：一个 chunk 文件里**多个 episode 合并进同一个 mp4**，
     resume 续采会另开一组文件 → "每回合每相机一个 mp4"的直觉是错的，
     校验应查"每路相机至少覆盖一个 mp4"。

3. **丢弃 episode 的异步写竞态（冒烟抓到的真 bug）**
   - 现象：A 键丢弃时 image_writer 报一串 `Error writing image ... No such
     file or directory`；
   - 真相：lerobot 的 `add_frame` 把 PNG 交给**异步**写线程
     （`AsyncImageWriter`），`clear_episode_buffer(delete_images=True)`
     自己会先排水但**只清 image_keys**；video 特征的临时目录是我手动
     rmtree 的，发生在排水之前 → 队列里的残留写在目录被删后才落盘；
   - 危害不只是报错：丢弃后立刻开新 episode（正常操作时序！），新回合
     写的是**同名路径** episode-000000/frame-000XXX.png，残留旧帧可能
     盖掉新帧 → 静默数据污染；
   - 修法：删目录前 `writer.image_writer.wait_until_done()`（修后冒烟
     ERROR 归零）；
   - 教训：**凡是自己绕过库的封装去动它的内部文件（临时目录），必须
     先补齐封装里隐含的同步语义**（这里的排水就是
     `clear_episode_buffer` 源码里 `delete_images=True` 分支在做的事）。

4. **无头冒烟方法论：stub 基类，其余全真**
   - 本机没有 XRoboToolkit，但 lerobot312 里 cv2/meshcat/placo/lerobot
     齐全 → 只 stub 一个包：假 `MujocoTeleopController`（真 MJCF + 假
     solver/任务对象 + 可编程 FakeXRClient），`calc_placo_q_from_mujoco_qpos`
     用 pinocchio `model.names`/`idx_q` 做真映射（注意 placo 的
     `model.joints[i]` 没有 `.name`）；
   - 这样 `H1PicoTeleopController` 的 `__init__`、X/A/B 分支、调度块全部
     真代码路径执行，还能真渲染真落盘真回读；`--check-model` 用同一套
     stub 跑通（TCP 对到 1e-8，顺带验证了 stub 映射的正确性）；
   - FakeXRClient 的按钮是 dict 字段，测试直接改值模拟上升沿，比 mock
     库轻得多。

5. **head_rgb 首帧"看不到机器人"是几何正确，不是渲染 bug**
   - 静态检查里 head_rgb 只见地面棋盘格+桌沿；查 XML：相机挂在
     Head_Link_j2，`xyaxes="0 -1 0 0 0 1"` = 平视前方（中性姿态水平，
     注释写明），75° fovy 平视时桌面方块在视野下缘 50° 以外；
   - 实机遥操作时头显姿态实时映射 head_j1/Head_j2
     （h1_pico_teleop.py `_update_upper_body_targets`），操作者低头
     head_rgb 自然俯视工作区 → 实采数据里头相机会看到双臂和方块；
   - 教训：判断"画面是否正常"要先算相机的**位姿+FOV 几何**，再谈
     渲染对错。

6. **X 键语义**（原工程 X 未使用，正好用作录制开关）
   - X 上升沿 toggle：未录→开始，录制中→保存结束；B 回零自动保存

   - 帧调度复刻工程里腕部相机的"仿真时刻调度"模式

## 22. 穿模+弹飞事故复盘（H1_build 手指碰撞体 box→mesh）

**现象（2026-08-18/19 实机 VR 遥操作）**：夹爪去抓桌上方块，肉眼看手指
还没碰到，方块已经被推走（"穿模"）；某次右手刚要夹住，红色方块直接弹飞。

### 真相：手指碰撞体是 AABB 盒，比真手指平均胖 6.35mm

排查路线：先对齐 `finger_collision` 的接触参数（margin/priority/condim/
solref/solimp 五件套逐字抄参考工程）→ 复测仍穿模弹飞 → 再比碰撞体**形状**：

| 部位 | 参考工程 | 我的 06 脚本(事故版) |
|---|---|---|
| 手臂/躯干 | 48% AABB 盒 ×21 | 48% AABB 盒 ✅ |
| 手指 8 件×2（**含耦合杆 loop**） | `type="mesh"` STL 凸包 ×16 | AABB 盒 ❌ |
| 夹爪座 mount（mesh=omnipicker_base_link） | 48% AABB 盒(`*_mount_collision*`) | (曾误判成"无碰撞体") |

盒角比真实指形提前 ~6mm 触发接触（`mj_geomDistance` 网格实测均值 −6.35mm，
78% 采样点"偏胖"），配上硬接触参数（solref 0.001）就是"看着没碰其实在推、
一碰就弹飞"。修法：06_collision.py 手指分支改出 `type="mesh"` 碰撞体，
重跑 06→07→11。

### 三个认知修正

1. **"拿 STL 当碰撞体必然自卡"是错误归因**。机器人不自碰的真正机制是
   defaults 的位掩码：`contype=0 conaffinity=1` 使任意两个机器人 geom
   的按位测试恒为 0，碰撞只发生在"机器人 vs 环境(contype=1)"之间。
   所以手指用 mesh 碰撞体完全安全，参考工程一直这么干。
2. **loop 耦合杆也要碰撞体**：它横在抓取口里，AABB 43mm 宽，比手指本体
   更容易先蹭到方块。参考工程 16 个 mesh 碰撞体含两个 loop 件。
3. **触觉 site ≠ 手指件全量**：touch site 只埋在 6 个真指尖件上（loop
   不埋），否则 07 按 site 数建 touch 传感器会把 nsensor 顶过 142 基准。

### 验证方法论：怎么证明"修好了且没修歪"

- **几何指纹（Step 12 固化）**：在"夹爪开度×方块位置"网格上，用
  `mj_geomDistance` 测方块到 8 根手指碰撞体的精确距离，与参考工程逐点
  对比。修复后平均偏差 **+0.04mm**、96% 点位 <±1mm → 等价；事故版平均
  偏胖 6.35mm。`mj_geomDistance(m, d, g1, g2, distmax, fromto)` 的
  fromto 没有 None 默认值，要显式传 `np.zeros(6)`。
- **教训：不要用"瞬移方块进指间再闭合"测抓取质量**。深重叠瞬移测的是
  求解器分离初始重叠的烈度：box 版直接把方块崩出 21 米，连参考工程都弹
  6.58 m/s。真实抓取的接触从表面零重叠开始，两类测试测的不是一回事。
- **IK 脚本化抓取也没做成**：工作空间边缘的"远处+大转角"目标会让 placo
  陷入局部极小（停在离目标 244mm 处一动不动，无异常无 NaN）；真实遥操作
  的目标是 clutch 锚定后连续增量更新，不会触发。另一个坑：180° 旋转矩阵
  的迹是 −1，教科书式 `quat()` 公式除零出 NaN，目标位姿 NaN 会让 IK
  静默自愈原地不动 —— 要用 Shepperd 四分支公式。
- home 姿态夹爪 ctrl=0 是**闭合**态；全开(ctrl=1)时指间净空也只比 40mm
  方块宽一点点，只有指尖区域塞得进 —— 这台 OmniPicker 抓 40mm 方块
  本来就是"几乎全开抓"。

### 第二轮："夹取有阻力、夹不上"（2026-08-19 同日）

mesh 修复后实机复测：不穿模不弹飞了，但夹方块"有阻力、夹不拢"。
这次不在几何层，在**动力学层** —— 全面 diff 两模型参数揪出三处：

| 参数 | 参考工程 | 我的(事故版) | 手感影响 |
|---|---|---|---|
| `noslip_iterations` | 10 | 0 | 接触面切向微滑不消除，方块在指间蠕滑，抓取发"酥" |
| `cone` | elliptic | pyramidal(默认) | 金字塔锥是线性近似，condim=6 的滚转/扭转摩擦失真 |
| equality `solimp` | 0.99 0.999 0.0001(硬) | 0.9 0.95 0.001(默认软) | 四连杆/对驱约束软 → 手指一压到方块就被接触力顶回，指尖回弹 |

根因都能追溯到"采购件 vs 调参件"：omnipicker_component.xml 出厂是软约束
（solref 0.005、solimp 缺省），前辈在最终模型里把每条 equality 手动调硬；
我的 05 脚本只覆盖了 solref，漏了 solimp。option 的 cone/noslip 同理——
04 脚本只抄了 timestep/integrator/iterations/tolerance 四项。

修法：04 的 `<option>` 补 `cone="elliptic" noslip_iterations="10"`；
05 的 equality 覆盖补 `solimp="0.99 0.999 0.0001"`。重跑 04→05→06→07→11
后逐项复验全对齐（含手指连杆质量、geom_gap、impratio、方块参数）。

**排查方法论**：手感类问题别猜，写一个"动力学参数全面 diff"脚本
（model.opt / 方块 geom / 夹爪执行器/关节/equality / 手指 geom 参数 /
连杆质量逐项打印对比），差异行自己会跳出来。另外注意：**chaos 测试不可
复现也不可比**——"瞬移方块进指间"的重叠分离速度在两次运行间能从 1.4 翻
到 11 m/s（同参数），这类测试只能看"是否灾难级"，不能看数值。

顺带记录：这台 OmniPicker 全开指间净空只比 40mm 方块宽一点，**夹住方块
时手指本来就停在半开**、有实实在在的接触反力——"夹到东西后有阻力"本身
是正常物理，修完这轮后它和参考工程的手感应当一致。
